# Грабли GB10: фризы, OOM и env-фиксы

Хронология инцидентов 14.09–18.09, причины и правила. Детали — артефакты в
`artifacts/gb10/` (ревью конфигурации) и локальный handover-пакет.

## 1. `#` внутри `command:`-блока compose = фриз нод (14–15.09)

YAML сворачивает строки `command:` в одну, и инлайн-комментарии `# ...` режут bash-команду:
vllm получал флаги только до `--gpu-memory-utilization 0.78`, теряя
`--tensor-parallel-size 2 --nnodes 2 --node-rank --headless` и dspark → движок стартовал
в одиночку (TP=1), модель не влезала в 128 ГБ unified → каскад
`NVRM: nvCheckOkFailedNoLog ... _memdescAllocInternal` → OOM-kill → клин ноды
(ssh мёртв, ping жив, журнал обрывается).

**Правило: `#`-комментариям не место внутри command-блока; строки с `#` — только с нулевой
колонки вне блока.** И не давать vllm-контейнеру автозапуск при буте, пока конфиг не проверен
(фриз-цикл «бутап → автостарт → фриз через ~1 мин» повторяется бесконечно).

## 2. NVRM-OOM на длинных префиллах (unified-память)

Ночь 17–18.09: на 478K-префилле `NV_ERR_NO_MEMORY` (mem_desc.c:1359) на обеих нодах.
Причины и фиксы:

- **Sparse-индексатор QSA** (гибридная Qwen-модель: 12 QSA-слоёв, n-gram 3, vocab 20M) без капа
  держал буфер логарифмов, растущий по чанкам; вешал ноду ровно на 166 400 токенах.
  Фикс: `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=64` — workaround апстрим-issue
  **vllm#56457** (автор — с этого же стенда). Плата: до 8 запусков кернела на чанк на слой
  при контексте >100K. Апстрим-фикс — PR #57105 (открыт).
- **Paдение «VllmWorker died, NVRM OOM»** → `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`
  (записано в шапке compose ~00:02 18.09).
- После фиксов чисто; контролировать: `sudo journalctl -k | grep -i nvrm`.

## 3. Пересоздание пары: gloo-гонка и порядок

Пересоздание воркера при живом старом head ломает пару на host-сети: воркер попадает gloo
в сокет СТАРОГО контейнера, после снятия старого head — `gloo Read error / Reset by peer`,
новый head вечно висит в NCCL-инициализации. **Канон: `down` на обеих нодах → up head →
~20 с → up worker.** (В пакете исторически было «worker first»; боевой канон 18.09 снят
с compose и `docker inspect` — head 00:03:55Z, worker 00:04:16Z.)

## 4. `--enforce-eager` обязателен

CUDA-graphs (full и piecewise) на sm_121 с NVFP4/FP8 вешают ноды и мешают MTP —
на паре всегда eager. Это осознанный выбор, не деградация.

## 5. Известные ограничения движка/драйвера

- **DeepGEMM** на sm_121 не заводится (JIT-зависание): для FP8-моделей — `VLLM_USE_DEEP_GEMM=0`.
  Для текущего пилота (NVFP4 modelopt) не актуально.
- **Драйвер 580.159.03** — регрессия (~3.5× падение) + NCCL RoCE regression
  (GID-таблица, падение в TCP; фикс `NCCL_IB_GID_INDEX=3`). На паре сейчас 580.173.02.
- **OOM при gpu-mem-util 0.95** гарантирован; 0.85–0.88 — рабочий диапазон; у пилота 0.80
  (запас на unified-систему, JIT, NCCL).
- **RDMA щипает память**: NCCL-буферы ~0.5 GiB больше TCP — учитывать в утилизации.

## 6. Нагрузочные грабли

- **earlyoom** на unified-машине при 100K-префиллах может убивать `VLLM::Worker`
  (RAM пилота ≈ памяти модели). Это страховка ноды, а не баг: жертвуем инференсом ради ноды.
  На время длинных тестов в пакете ранние отключения earlyoom; мы так не делаем — только
  по согласованию.
- **SSH зависает на время загрузки** крупных моделей (давление на unified RAM) — ждать 10–15 мин.
- **JIT-спайки**: после холодного старта тритоновские кернела компилируются на лету до 1–2 ч
  (пример: `_topk_topp_kernel` скомпилировался при новом сэмплинг-параметре запроса в 12:12
  следующего дня). Warmup не покрывает все формы; при бенчах — прогревать формы заранее.
